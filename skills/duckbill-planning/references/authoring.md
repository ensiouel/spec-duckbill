# Planning Authoring

Read the complete ready specification before choosing design. If it is draft or contains an unresolved material product
decision, stop and report specification as the owner.

Initial planning MUST NOT overwrite an existing substantive `plan.md` or `tasks.md`. If either already contains planning
work, stop and report planning refinement as the appropriate operation.

Inspect the actual repository before finalizing the plan. Examine relevant source files, modules, symbols, interfaces,
similar implementations, tests, configuration, project conventions, dependencies, and safe verification commands.
Existing paths and symbols MUST NOT be invented; identify new ones as new.

Choose the smallest coherent technical design that satisfies the specification. Resolve technical choices through
repository evidence and engineering judgment. Ask a focused question only when a material planning decision cannot be
responsibly determined from the specification, project instructions, and verified facts.

Create or establish `plan.md` and `tasks.md` together because task decomposition derives from design. Use the assets as
adaptable starting points, omit irrelevant sections, and replace every placeholder.

Check that execution can proceed without inventing architecture, component ownership, integration, persistence,
dependency strategy, important paths, or verification approach. Ensure tasks collectively cover every current
requirement and acceptance criterion with meaningful implementation outcomes.
